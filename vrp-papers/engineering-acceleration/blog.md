## 策略 1：基状态热启动（Basis Warm-Start）

收益最大的单一策略，也是最容易被忽略的。

### 原理

单纯形法（simplex）求解 LP 的过程是在可行域多面体的顶点间跳转（pivot）。CG 每轮只加几列，新旧模型极其相似。如果把上一轮的最优顶点位置告诉求解器，它通常 1-3 步跳转就到新最优，而不是从零开始。

热启动有三个层次，区别在于给求解器的信息精度不同：

| 方式 | 给求解器什么 | 求解器要做什么 | 实测加速 |
|------|------------|-------------|---------|
| 冷启动 | 无 | 从零开始寻找最优解 | 1×（baseline） |
| 解向量 | 上一轮各变量的取值（λ₁=0.5, λ₂=0.3, ...） | 知道变量的值，但不知道哪些在基中——需要反推基结构（称为 crash），才能开始跳转 | 5.5× |
| **基状态** | **每个变量是否在基中**（一个整数状态数组） | **直接知道站在哪个顶点上，零开销，立刻开始跳转** | **11.5×** |

两者的区别：单纯形法的"顶点"由基结构（哪些变量在基中）唯一确定。解向量只给了坐标值，求解器还得反推出基结构，这个过程有开销；基状态直接给出基结构，省掉了这步反推。

### 实现

```cpp
// CG 每轮：保存旧基 → 加列 → 恢复旧基 → 求解
std::vector<int> vbasis, cbasis;
solver->getBasis(vbasis, cbasis);    // 保存

solver->addColumn(cost, coeffs);     // 加新列
solver->update();

solver->setBasis(vbasis, cbasis);    // 恢复（新列默认 non-basic）
solver->solveLP();                   // 1-3 步 pivot
```

### 踩坑

**`addVar()` 后 Gurobi 不会自动继承旧基**，必须手动保存/恢复。这在文档里很容易被忽略，但不做的话 warm-start 完全失效。

另一个常见误区是"需要关闭 Presolve 才能 warm-start"。在旧版本确实如此（presolve 重编号变量，破坏 basis），但 Gurobi 11+ 的 `Presolve=auto` 模式会智能判断——检测到 basis 时自动跳过 presolve，没有 basis 时才做 presolve。实测 auto 比强制关闭还快 2-15%。

类似地，`Method=1`（对偶单纯形法，dual simplex）是列生成场景的自然选择——加列和加行都保持对偶可行性，对偶单纯形法可以直接从对偶可行的旧基出发，不需要额外找可行解的步骤。实测 +1-3%，一行代码的事。

### A/B 数据

| 实例 | warm=OFF | warm=ON | 提升 |
|------|----------|---------|------|
| E-n13-k4 | ~400 nodes/s | ~800 nodes/s | **~2×** |
| P-n16-k8 | ~970 nodes/s | ~1920 nodes/s | **~2×** |

## 策略 2：约束批量更新

### 原理

B&B 分支时，需要给 RMP 加/删约束（forced/forbidden edge）。如果每加一条就调一次 `solver->update()`，求解器每次都要内部重构模型数据结构。攒起来一次 `update()` 就只重构一次。

### 实现

```cpp
// 之前：循环内逐条 update
for (auto& edge : branch_edges) {
    solver->addConstraint(...);
    solver->update();  // 每条都重构，慢
}

// 之后：批量 update
for (auto& edge : branch_edges) {
    solver->addConstraint(...);
}
solver->update();  // 只重构一次
```

### A/B 数据

| 实例 | 逐条 update | 批量 update | 提升 |
|------|-----------|------------|------|
| E-n13-k4 | baseline | — | **+8%** |
| P-n16-k8 | baseline | — | **+8%** |
| P-n23-k8 | baseline | — | **+24%** |

实例越大、分支约束越多，收益越明显。

## 策略 3：Farkas 定价

### 问题

Edge branching 的 force 分支（强制某条边必须被使用）经常导致 RMP 不可行——当前列集中可能没有包含这条边的路线。

传统做法是给每个覆盖约束加一个 Big-M 人工变量（`obj = 1e6`），保证 LP 始终有可行解。但 Big-M 会**污染对偶值**：人工变量在基中时，对偶被 1e6 量级的 obj 拉歪，用这个对偶去定价，生成的列质量差，甚至可能让 CG 多跑好几轮。

### 原理

LP 不可行时，有两种恢复策略：

**Big-M 法**：给约束加人工变量（目标系数 1e6），把"恢复可行性"和"优化目标"混在一个 LP 里求解。问题是：人工变量在基中时，对偶值被 1e6 量级的系数拉偏，拿这个对偶去定价，生成的列质量差。

**Farkas 法**：求解器报告不可行时，可以提取 **Farkas 不可行证书**——一组对偶值，纯粹反映"哪些约束最难满足、缺口多大"。用它做定价，生成的列直接针对可行性缺口，即**最能恢复可行性的路线**。数学上，Farkas 对偶等价于"最小化总不可行量"这个辅助 LP 的最优对偶解，比 Big-M 精确得多。

```cpp
if (lp_status == INFEASIBLE) {
    // 不用 Big-M 对偶，而是提取 Farkas 证书
    std::vector<double> farkas_duals(n_constrs);
    for (int i = 0; i < n_constrs; i++)
        farkas_duals[i] = solver->getFarkasDual(constr_ids[i]);

    // 用 farkas_duals 做定价 → 生成恢复可行性的列
    auto cols = pricing(farkas_duals);
    // 加入后重新求解，通常 1-2 轮恢复可行
}
```

### A/B 数据

| 实例 | 无 Farkas | 有 Farkas | 提升 |
|------|---------|---------|------|
| E-n13-k4 | 537 nodes/s | 586 nodes/s | **+9%** |
| P-n16-k8 | 968 nodes/s | 1095 nodes/s | **+13%** |

提升来源：减少了 CG 中因 Big-M 对偶偏差导致的无效迭代轮次。

## 策略 4：列池管理——多列添加与去重

### 多列添加

教科书 CG 每轮只加 1 列（rc 最负的那条）。但定价一次能找到很多负 rc 列，只取一条意味着丢弃了本轮定价的大部分产出，下一轮对偶变了之后还得重新定价才能重新发现它们。

为什么多加的列不会"浪费"？因为 CG 的瓶颈在定价（ESPPRC），不在 LP 求解。每轮 CG 的固定开销是一次定价 + 一次 LP solve。多加 k 列，LP 规模略增但定价次数减半甚至更少——净效果是强正的。而且实践表明，当轮的负 rc 列大部分在后续轮次仍然有用（rc 仍然为负或接近零），因为它们是最优路线的"结构邻域"。

```cpp
auto neg_cols = pricing(duals);       // 定价返回所有负 rc 列
for (auto& col : neg_cols)
    rmp.addColumn(col.cost, col.visits);  // 全部加入
```

这不是优化技巧，而是**标准实践**——BaPCod/VRPSolver 等成熟框架默认就是多列添加（Root 节点每轮最多加 2000 列，非 Root 加 100 列）。

### 列去重

CG 前期对偶值经常**震荡**：第 1 轮 π₃ = 0，第 2 轮跳到 π₃ = 50，第 3 轮又回到 π₃ = 5。这是因为 RMP 列数远少于约束数，对偶解不唯一，每加一列对偶就大幅跳转。震荡的对偶意味着不同轮的定价环境可能"轮回"，生成出一模一样的路线。

重复列已经在 RMP 里了，再加一份只增加 LP 规模，没有任何好处。用哈希表在加入前过滤：

```cpp
size_t hash = std::hash<int>{}(col.cost);
for (int v : col.visits)
    hash ^= std::hash<int>{}(v) + 0x9e3779b9 + (hash << 6) + (hash >> 2);

if (seen_hashes.count(hash)) continue;  // 已存在，跳过
seen_hashes.insert(hash);
rmp.addColumn(col.cost, col.visits);
```

这里不存在"死循环"的问题：被跳过的列并没有被丢弃——它的第一份已经在 RMP 中了。去重只是防止加入第二份副本。原始列仍在模型里约束着对偶空间，LP 求解后对偶会继续变化，下一轮定价自然产出不同的列。

多列添加让 CG 收敛更快，去重防止列池膨胀——两者配合是列池管理的基本功。

## 综合效果

### 单策略 A/B 汇总

| # | 策略 | E-n13-k4 | P-n16-k8 | 代码量 | 泛化性 |
|---|------|----------|----------|--------|--------|
| 1 | 基状态 warm-start | **~2×** | **~2×** | ~15 行 | 任何 CG 都有效 |
| 2 | 约束批量更新 | +8% | +8% (+24% @P-n23) | 改几行 | 任何 B&B 都有效 |
| 3 | Farkas 定价 | +9% | +13% | ~30 行 | 有 Big-M 人工变量就有效 |
| 4 | 多列添加 + 去重 | 标准实践 | 标准实践 | ~20 行 | 任何 CG 都有效 |
| — | Dual simplex + Presolve auto | +3-15% | +3-15% | 各 1 行 | LP 求解器标准配置 |

### 端到端效果（E-n13-k4, 30s 限时）

| 指标 | 策略全关 | 策略全开 | 变化 |
|------|---------|---------|------|
| B&B 节点数 | 4,910 | 26,203 | **5.3×** |
| 平均 simplex 迭代/LP | 22.5 | 6.2 | **-72%** |
| 节点吞吐 | 164 nodes/s | 873 nodes/s | **5.3×** |
| 最优解 | 290 ✓ | 290 ✓ | — |
| 证明最优 | 30s 未证明 | 30s 未证明 | — |

工程策略的作用一目了然：每次 LP 求解的 simplex 迭代从 22.5 降到 6.2（warm-start 的功劳），同样时间内多探索了 5 倍节点。

但两组都**未能在 30s 内证明最优**（LB 停在 287，gap 1%）——工程策略提速了"搜"的效率，但没有减少"要搜的量"。要真正缩小 B&B 树，需要的是算法层面的改进：cuts 收紧 LP bound、列裁剪减少无效节点——这些留给后续。

总计约 80 行代码改动，实现简单、收益确定，是后续所有算法加速的工程基础。

## 总结

本文介绍的 5 个策略都是"怎么跟求解器打交道"和"怎么管列池"的工程技巧，不涉及算法创新。它们的共同特点是：实现简单、效果确定、跨问题泛化。

总计约 80 行代码改动，换来 2-3× 的整体加速。在后续叠加算法层面的加速（ng-route、cuts、对偶稳定化等）时，这些工程基础不会失效——它们是"地基"，算法策略是"楼层"。
